**Overview**

Settle four anchors: Goal (why this matters), Scope (what is in and what is explicitly out), Functional outcome (what someone can observe when it is done) and Repos (which repositories change). An anchor is settled only when the ticket states it explicitly and unambiguously, or only one option is viable; otherwise ask. Treat the project's direction and preferences as defaults to confirm, not gaps to ask about cold. Never infer repositories the ticket and project do not name.

Imagine the realistic outcomes the person could want from this ticket, then ask to narrow them to one. "In scope" is the complete set that must change together for the feature to work everywhere a user meets it; each thing left out is named as a deliberate divergence.

**List the open anchors**

For each anchor, write what the ticket already settles and what is open.

**Ask**

Ask about the open ones. If an answer stays vague, offer to proceed with what you have or stop.

**Check the ripples**

Anything the change would force in a repository nobody named is flagged to the person, never silently added.
