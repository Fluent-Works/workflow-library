A migration ships with code only when the live server can serve before, during and after it; the project description or README says how this repository applies migrations (by the deploy itself, by a workflow after it, or by hand), and that decides what may merge.

Expand first, contract later. A new table, a nullable column or a column with a constant default may ship in the same pull request as the code that reads it, provided the migration is applied before that code serves a request: a deploy that migrates first, or a hand run before the merge. If the migration would run after the new code is live, or someone has to run it by hand and has not, merge nothing and ask: the new code would select columns the database lacks and every read fails. A drop or a rename of anything the live server still reads never ships with the code that stops reading it; that code deploys first and the drop follows in a later pull request, because the old server keeps serving until the deploy switches over.

Before merging, read the pull request's migration files and its Rollout section against these rules, not only the description's word for it. Each migration file should hold statements that run in one transaction, which is how migrators apply them; a concurrent index on a large table is its own hand step. A rollback of the deploy leaves the schema in place, which is safe exactly when the migration was additive.
