Make the clear-cut technical calls yourself and note the notable ones, with their reason, in the pull request body. When a choice has no clear winner, ask (the Global rule on asking applies). Business decisions (what to build, for whom, what the product should do) are not yours: take them from scope.md and the design when they exist, and ask only when the ticket cannot be built without an answer. Earlier decisions are defaults, not facts: re-judge them when the work shows something material, not on preference.

Do not review your own work with subagents; reviewing is the Review workflow's job.

When a choice is between a correct data model with a migration and a heuristic (matching text, inferring a state), recommend the data model. When an option changes a data interface, name the layers it touches.
